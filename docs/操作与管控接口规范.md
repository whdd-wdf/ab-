## 1. 订单队列 `/root/monitor/order_queue/`

**唯一入口，操作侧执行订单的唯一来源。**任何要华为执行（经笔记本下单）的订单，必须以 JSON 文件形式进入 `pending/`；执行器不接受任何其他形式的订单（没有 API、没有命令行直下单接口）。

### 1.1 目录与文件

| 目录 | 含义 | 写者 | 读者 |
|---|---|---|---|
| `/root/monitor/order_queue/pending/` | 待执行订单，每文件一单 | 沙箱 `queue_order.py submit`、华为 `b_intraday_trigger.py`（live/dryrun）、华为 `fillwatch_rehang.py`（live） | `order_executor.py`（经 `order-watcher.path` 触发） |
| `/root/monitor/order_queue/done/` | 已执行（或 dry-run 通过）的订单，原订单 + `result` | `order_executor.py`（移入） | 管控侧（`queue_order.py status`、hook `b-intraday-done`） |
| `/root/monitor/order_queue/failed/` | 被拒绝/失败/过期/门关的订单，原订单 + `result` | `order_executor.py`（移入）、门控关门（plain mv，无 `result` 注解） | 管控侧（同上） |

- 文件名 = `<order_id>.json`，与文件内 `order_id` 字段一致。

### 1.2 订单 JSON 格式（已核实：`queue_order.py` 源码 + 华为 `done/` 真实样本）

必填字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `order_id` | 字符串 | 订单唯一标识，见 1.3 命名规则；文件名与此一致 |
| `code` | 字符串 | 6 位代码，如 `600919`、`601088`、`510300`、`513650` |
| `side` | 字符串 | 恰为 `买入` 或 `卖出` |
| `price` | 数字 | 限价（元）。B 线卖单为触发器算出的限价；A 线为节点价或节点价×1.02 |
| `qty` | 整数 | 股数 |

可选字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `limit_price` | 数字 | B 线买入 P4 限价（合规校验 `买价<=P4限价` 用；不传则该项跳过并注明） |
| `prev_close` | 数字 | 前收价（合规算涨幅/涨停用；不传则取实时行情，取不到则该项跳过并注明） |
| `line` | 字符串 | `A` 或 `B`（合规分流用：A 线代码走节点价校验，B 线走 B 线校验；见 1.5） |
| `note` | 字符串 | 备注。B 线触发单格式定死为 `盘中触发<level><止损/止盈>卖出<一半/全部>，5分钟收盘确认，订单<order_id>`（须含档位字样与订单号，hook 入账去重靠它） |
| `dry_run` | 布尔 | `true` 时只走合规、不调笔记本、不下单（默认 `false`） |

### 1.3 `order_id` 命名规则（已核实：三处写单代码）

| 来源 | 格式 | 示例 |
|---|---|---|
| B 线盘中触发（live） | `SELL-<YYYYMMDD>-<代码>-<档位>-<序号>`，档位 ∈ `S1`/`S2`/`+3%`/`+5%`，序号 1 起 | `SELL-20261113-600919-+3%-1` |
| B 线盘中触发（dryrun） | `DRY-<YYYYMMDD>-<代码>-<档位>-<序号>`，订单带 `dry_run=true` | `DRY-20261113-600919-S1-1`（格式据 `b_intraday_trigger.py`，未实测产出） |
| A 线 fillwatch 补挂（live） | `FW-<YYYYMMDD>-<代码>-buy/sell-<价，`.`→`p`>-<委托时间YYYYMMDDHHMMSS>` | `FW-20261113-601088-buy-48p61-20261113083619` |
| B 线早盘/尾盘任务（经 `queue_order.py`） | 调用方自定，须唯一；B 线卖单沿用 `SELL-<YYYYMMDD>-<代码>-<档位>-<序号>` | 见 `b_intraday_huawei_plan_20261113.md` §1.1 |
| 一次性测试单 | 调用方自定 | `B-REALTEST-1113` |

- 序号递增规则（B 线触发）：同一 code+level+日重试时 +1，依据是读当日 `pending/`、`done/`、`failed/` 中同前缀文件个数；**触发器本轮只写 `-1`**，重试由 hook worker 发起时才 +1（`b_intraday_trigger.py` 源码）。
- **去重键：执行器不做全局去重。**同一触发若被两个写单方各写一次，会产生两笔不同 `order_id` 的订单，合规都会放行（B 线卖出不校验重复在挂，重复校验只在 A 线分支）。防重靠三层，各在各的接口里写明：① 并行期华为触发器 compare 模式不写 pending（P1-2）；② fillwatch live 时 state + 队列去重（已下发的成交不再算、已在 pending/done 的不重排，见 §4.5）；③ hook 入账去重（trade_log grep `order_id`，见 §7.4）。**管控侧写单前必须确认自己是唯一写单方；双 live 并行是明令禁止的状态。**

### 1.4 状态流转（已核实：华为 `/root/monitor/order_executor.py` 源码，2026-11-12 门控版）

```
pending/*.json
├─ 门关（标志缺失/过期，或不在 07:30–17:05）──→ failed/{result:{status:"gate-closed", reason:"…"}}
├─ 文件 mtime 非当日 ──────────────────────→ failed/{result:{status:"stale", reason:"订单非当日（…），过期"}}
├─ 合规不通过 ────────────────────────────→ failed/{result:{status:"rejected", reasons:[…], checks:[…]}}
├─ dry_run=true 且合规通过 ────────────────→ done/{result:{status:"dry-run-pass", placed:false}}
├─ 笔记本下单 rc=0 ───────────────────────→ done/{result:{status:"placed", laptop:{…}}}
└─ 笔记本下单失败 ────────────────────────→ failed/{result:{status:"laptop-failed", rc:N, stdout:"…", stderr:"…"}}
```

- 执行器流程（`process_one`）：读 pending JSON → `run_compliance()`（`python3 /root/monitor/order_compliance.py --order '<json>'`，timeout 300s）→ 非 pass 移入 failed；dry-run 移入 done；否则 SSH 笔记本 `ssh -o ConnectTimeout=30 -o BatchMode=yes -o StrictHostKeyChecking=no madaha@100.90.180.87 'cd /home/madaha && python3 laptop_order.py sell <code> <price> <qty>'`（买入为 `buy`），timeout 600s。
- **合规不通过或下单失败，执行器不重试。**重试责任在管控侧（B 线 attempts 机制，见 §7.4；A 线补挂失败由主代理/下一定时任务处理）。
- 订单 JSON 解析失败时，执行器用 `{order_id: <文件名>}` 兜底再移入 failed（不丢弃无记录）。
- 执行器日志：`/root/monitor/order_executor.log`（同时 stdout）；watcher 日志：`/root/monitor/order_watcher.log`（TRIGGER 行）。
- 沙箱查结果：`python3 queue_order.py status <order_id>`，按 `done` → `failed` → `pending` 顺序 `test -f`，done/failed 时 `cat` 返回 result；输出 `{"status":"pending"|"done"|"failed"|"not_found","result":{…}}`。`status` 为 `pending` 时 `result` 为 null。
- 沙箱写单：`python3 queue_order.py submit --order-id X --code … --side 买入/卖出 --price … --qty … [--limit-price …] [--prev-close …] [--line B] [--note "…"] [--dry-run]`；流程：本地写 `/tmp/queue_order/<order-id>.json` → rsync 到华为 `pending/` → 远端 `ls -l` 复核；任一步失败即报错返回，不静默。

### 1.5 合规校验清单（已核实：华为 `/root/monitor/order_compliance.py` 源码）

调用方式：`python3 /root/monitor/order_compliance.py --order '<订单JSON>'`（或 stdin 读 JSON），timeout 300s。规则通过后走 LLM 合理性复核（`llm_reasonableness`）：判 `unreasonable` 才 reject；**超时/失败/解析失败 → fail-open 放行**。

A 线订单（`line=A` 或代码为 510300/601088/513650）：

| 校验 | 口径 |
|---|---|
| 买入：买价=节点价 | 买价须为账本节点价；例外：节点价低于当日跌停时按跌停价挂亦可 |
| 买入：买入<=grid_available | 金额 ≤ 该仓 `grid_available`（quota.py）；quota 取不到则拒绝 |
| 买入：单笔>=5000 | `MIN_AMOUNT = 5000.0`（全局） |
| 卖出：卖价=节点价×1.02 | tick 取整后比对（510300/513650 tick 0.001，601088 tick 0.01） |
| 卖出：卖出<=可卖量 | 数量 ≤ 账本该仓“可卖”行（读节点账本文件，不读 trade_log） |
| 卖出：卖价<=涨停 | 涨停 = 前收×1.10 tick 取整；前收取不到则跳过并注明 |
| 卖出：卖价不重复在挂 | 与最新 fillwatch 快照 `orders` 中同代码同方向 `未成交` 行比价；无快照则跳过并注明 |
| 卖出：非禁挂集群价 | `BANNED_PRICE = {"510300": {4.316, 4.324, 4.325}, "601088": {52.06}}` |

B 线订单：

| 校验 | 口径 |
|---|---|
| 买入：涨幅<=5% | `price/prev_close - 1 <= 0.05`，超则硬过滤；前收未取到则跳过并注明 |
| 买入：买价<=P4限价 | 仅 `limit_price` 传入时校验；不传则跳过并注明 |
| 买入：买价≈现价 | `abs(price/当前价 - 1) <= 0.01`，超则拒绝；当前价取最新快照/行情，取不到则跳过并注明（防串价错单） |
| 买入：单笔<=5万 | `B_SINGLE_LIMIT = 50000.0` |
| 买入：买入<=B可用 | 金额 ≤ quota.py B 线 `available`；quota 取不到则拒绝 |
| 买入：B线<=3只 | 新开仓（代码不在持仓中）时持仓只数 < 3，持仓由 trade_log 推算（见 §2） |
| 卖出：卖出<=持仓 | **唯一校验**，数量 ≤ `b_holdings()[code]`（trade_log + huawei_bookings 两份推算）；价格、档位、涨停、重复在挂均不校验——限价正确性必须由监盘侧保证，不能依赖合规兜底 |

**真实算例（2026-11-13 601088 成交，防只复述不验算）**：卖出 200 股，节点价 48.61，委托价 49.58，成交 09:41:18，补挂买单 200 股 @48.61，挂出 09:46:12。逐项算出数字再写结论，不许只写“根据 X 确认……”而不验算：
- 卖价 = 节点价×1.02：48.61 × 1.02 = 49.5822，tick 取整（601088 tick 0.01）= 49.58，与委托价 49.58 一致 ✓
- 补挂买价 = 节点价：48.61 ✓
- 单笔金额 = 200 × 49.58 = 9,916 ≥ 5000 ✓
- 补挂延时 = 09:46:12 − 09:41:18 = 4 分 54 秒，在 4–6 分钟目标内 ✓

**关键数字由程序算、AI 只做判断（2026-11-13 盒内复测教训）**：管控侧做选股/把关/辩论时，涨幅、P4、股数、金额等数字一律取程序输出（如虚拟程序 `check` 接口），AI 不自己算；定稿前复述“代码—名称—现价”三元组并与程序输出比对，不一致即停；辩论前先由程序复核数据（三元组、涨幅、P4、股数、金额），任一不符直接跳过、不进辩论。3B 模型多位数小数运算系统性不可靠，算数是程序的事。

**出错时怎么办**：合规 reject 的订单进 `failed/`，`result.reasons` 列明每条失败原因，`result.checks` 列明逐项校验结果。管控侧读 `reasons` 定性：规则性拒绝（价格/额度/持仓）→ 修单重提或放弃；LLM 复核拒绝（reasons 含 LLM 字样）→ 主代理定夺是否人工重提；`gate-closed`/`stale` → 见 §5。

### 2.2 列格式（已核实：真实文件，776 行，2026-11-13 10:2x）

表头（9 列，固定顺序）：`日期,代码,名称,方向,价格,数量,金额,盈亏,备注`

5. **本脚本只读华为 bookings（cat），只追加沙箱 trade_log，归档只动华为 bookings 文件；绝不写华为 trade_log 副本。**

### 4.3 stale 判定与读方

- **stale 判定**：快照 `timestamp` 距现在 > **300 秒（5 分钟）** 即 stale。沙箱 hook（`fillwatch`，poll 60s，`fillwatch_compare.py`）对 stale 快照唤醒告警（同一份错误快照按 timestamp 消重，只唤一次，10 分钟后可再唤）；华为 `fillwatch_rehang.py` 对 stale 快照只记 verdict、不计算、不唤醒（告警仍由沙箱 hook 负责）。

## 5. 门控标志 `/root/monitor/.trading_day`

### 5.1 含义与写者

- **文件**：华为 `/root/monitor/.trading_day`，**空文件**，内容无意义，**mtime 的日期就是全部含义**：mtime 日期 = 当日 ⇔ 今日交易日已开门；文件不存在或 mtime 非当日 ⇔ 门关。
- **写者（双写并行，幂等设计）**：
- 沙箱 gate：`monitor-gate-open`（交易日 07:30）`touch`；`monitor-gate-close`（17:05）`rm -f`。2026-11-13 实查：标志 mtime `2026-11-13 07:25:54.863858623`（沙箱 gate 写的）。
- 华为自备门控：`/root/monitor/gate_local.py`（P1-1），`gate-local-open.timer`（Mon-Fri 07:30）/ `gate-local-close.timer`（Mon-Fri 17:05），`Persistent=false`。开门见当日标志即跳过、不覆盖、不回写；重复开门是真空操作（mtime 分毫不差）。
- **受控的 4 个单元**（两边同一清单）：`order-watcher.path`、`cofool-fillwatch.timer`、`cofool-monitor-closecheck.timer`、`cofool-monitor-fillcheck.timer`。开门 `systemctl enable --now` 4 单元 + 写标志；关门 `disable --now` 4 单元 + `rm -f` 标志 + pending 残留移入 failed。
- **不归本门管**：`migration-phase1-sync`（数据管道）、`camofox-prestart.timer`（维护性）、runonce 一次性任务、笔记本 Chrome 常驻；以及 `b-intraday-monitor.timer`（P1-2 未决点 2：是否纳入待主代理定，见 §7.5）。

### 5.2 执行器凭标志的判定（已核实：`order_executor.py` `gate_open()`）

```python
FLAG = /root/monitor/.trading_day
OPEN_MIN = 7*60+30 # 07:30
CLOSE_MIN = 17*60+5 # 17:05
# 标志存在且 mtime 日期 == 当日，且当前时间在 07:30–17:05 内，否则拒绝
```

- 门关时：队列非空则**整批拒绝**，全部 pending 移入 failed（`result={status:"gate-closed", reason:"…"}`），日志记 `GATE-CLOSED …：拒绝执行，N 笔移入 failed`。
- 单个订单文件 mtime 非当日 → 移入 failed（`result={status:"stale", reason:"订单非当日（…），过期"}`），日志记 `STALE …`。
- **出错时怎么办**：门关导致的 failed 不是订单本身的问题，次日不得直接重提——须先查门为什么没开（gate 日志、交易日判定），再由管控侧按当日规则重新决策。

### 5.3 关门 pending 处理与并行安全（已核实：`gate_local.py` docstring + P1-1 记录）

- 关门时 pending `*.json` plain mv 进 `failed/`（**无 result 注解**，与沙箱 close 同口径；执行器自己的 gate-closed 路径才加注解）。
- 双关门并行（沙箱 gate-close 与华为 gate-local-close 同一分钟触发，设计内并行）：逐文件 `os.rename`；对端已移走的文件触发 FileNotFoundError → 记 skip、不报错；`failed/` 已有同名文件时绝不覆盖，改存 `<name>.dup-<epoch>.json`。
- 本地并发：`flock`（`.gate.lock`，非阻塞）；抢不到锁直接 rc 0 静默退出，由持锁方完成工作。
- 开门 `enable` 两次失败才返回 1，且**不写标志**（fail-closed，与沙箱 `&&` 链同义）；非交易日开门只做关闭扫尾（`disable --now` + `rm -f` 标志，**不移 pending**）。

### 5.4 交易日判定（已核实：`gate_local.py` docstring + `is_trading_day.py`）

- 判定脚本：华为 `/root/monitor/is_trading_day.py`（由已同步副本复制，与沙箱版一致；日历脚本本身未改一字，未自编交易日历）。
- 判定口径：sina_calendar（rc 0）为准；weekday_fallback（rc 2，akshare/sina 取数失败）按工作日 fail-open 并记入日志；脚本缺失/解析失败/超时 → 本地按周一至五兜底并记 WARN。
- 华为运行环境：华为系统 python3 无 akshare（PEP 668 拦下系统 pip），日历脚本跑在 `/root/monitor/gate-venv/`（akshare 专用 venv）；venv 缺失时回落系统解释器（退化为 weekday_fallback，不崩）。
- 日志：`/root/monitor/gate_local.log`（dry-run 不写文件，只打 stdout）。
- **遗留风险**：新浪日历取数失败时 fail-open——工作日节假日会误开门。缓解：沙箱 gate 仍为主用（其 sina 校验独立），且误开门当日无订单来源时无实际执行；17:05 关门照常执行。建议：gate 日志中 FALLBACK 行由主代理定期巡检。
