## 1. fillwatch 3 项失败：现象、根因、修复

接手时 fillwatch 7 项中失败 3 项（2026-11-14 07:38 笔记本实测）。

### 失败 1：补挂 order_id 价格格式错

- **现象**：测试期望 `FW-20261113-601088-buy-48p61-…`，实得
`FW-20261114-601088-buy-49p-20261114073835`。
- **根因（代码错＋测试日期过期，两处）**：
- 代码：`fillwatch_rehang.py` 卖出成交→补买分支用
`"FW-%s-%s-buy-%dp-%s" % (…, node_price * 1.02, …)`。
买单价本应是节点价本身（48.61），代码却用了卖价公式（48.61×1.02=49.58），
再经 `%d` 截断成 49，得 "49p"。买入成交→补卖分支同理（卖价 49.58 应为 "49p58" 却成 "49p"）。
参照：华为 `fillwatch_rehang.py` 用实际补挂价 `supp_price`，`.`→`p`；
接口规范 §1.3 亦同（`FW-<YYYYMMDD>-<代码>-buy/sell-<价，`.`→`p`>-<委托时间>`）。
- 测试：期望写死 `20261113`（写于 2026-11-13），当日已是 2026-11-14，
代码用快照日期生成 `20261114` 是对的。
- **修复**：
- 代码：买单 order_id 改用 `str(node_price).replace(".", "p")`；
卖单改用 `str(round_tick(price * 1.02, TICK)).replace(".", "p")`。
- 测试：期望日期改为 `datetime.date.today()` 动态生成。
- （注：order_id 末段仍用 `now` 而非成交单委托时间，与接口规范 §1.3
“委托时间”有偏差，属遗留小项，不影响本次 3 项修复；已记入 §6。）

### 失败 2：已入账成交应静默

- **现象**：代码返回 `verdict="no_new_fills"` 且无 `reason` 字段；
测试要 `verdict="silent"` 且 `reason="no_new_fills"`。
- **根因（代码错）**：`make_verdict` 把 `reason` 参数直接塞进 `"verdict"` 字段，
不设独立 `reason` 字段。规范（接口规范 §375 与华为参照）是两字段分开：
`verdict` ∈ silent/computed/blocked/emitted/error，`reason` 为具体串。

### 失败 3：过期快照应静默

- **现象**：代码返回 `verdict="stale_snapshot"`；测试要 `verdict="silent"`
且 `reason="stale_snapshot"`。
- **根因**：同失败 2（`make_verdict` 结构错）。

### 失败 2、3 的统一修复

重写 `make_verdict` 的 verdict/reason 映射：
- `reason="computed"` → `verdict="computed"`，`reason="computed_compare_only"`（compare 模式）；
- `reason` ∈ no_snapshot / stale_snapshot / outside_window / no_new_fills
→ `verdict="silent"`，`reason` 保留原串；
- 其余 → `verdict="silent"`。

## 2. 附带修复：gate 测试日期过期（4 项失败）

- **现象**：`test_gate.py` 注释写死“今天 2026-11-13 是周五”，`status`/`open`
不传 `--date`，用当日判定；当日是 2026-11-14 周六，`trading_day=false`，
故“status 交易日为真（周五）”“open 写标志”“status 门开”“标志过期则门关”4 项失败。
`gate_local.py` 的 `status` 命令不接受 `--date`（只 `open` 接受），且 `open`
的交易日判定也不用 `--date`（只用它写标志日期），`write_gate_flag` 的 mtime
恒为当前时间。
- **修复**：
- `gate_local.py`：`cmd_status` 接受 `date_str`，交易日判定与标志 mtime 比对
均按指定日期；`cmd_open` 的交易日判定改用 `date_str`；
`write_gate_flag` 指定日期时 mtime 设为该日中午（测试用），否则为当前时间；
CLI `status` 透传 `args.date`。无 `--date` 时行为与原来完全一致（生产不受影响）。
- `test_gate.py`：周五检查统一传 `--date 2026-11-13`；“昨天” mtime 改为
相对模拟日期的 2026-11-12 中午（原 `time.time()-86400` 是相对真实当日，
在周六跑会撞上模拟日期）。

## 4. 对接验证：模拟成交闭环（17/17）

新增 `~/sys2/monitor/tests/test_integration.py`。

### 闭环用的是哪套虚拟程序、怎么模拟的

- 虚拟程序：`~/sys2/control/virtual/`（`virtual_ops.py`，与第 3 步同一套）。
- 闭环链路（全程模拟成交，不依赖真实成交）：
1. 监管出单：虚拟 `submit` 卖 601088 200@49.58（A2 节点卖单，订单 T-I1）。
2. 虚拟成交：虚拟 `run` 模拟成交（只改 state 为“已成交”，模拟真实成交
发生在 cofool），虚拟 `snapshot` 生成快照。
3. fillwatch 检出新成交：`fillwatch_rehang.py --mode compare` 检出 T-I1，
算出补挂买单 200@48.61，order_id `FW-20261114-601088-buy-48p61-…`。
4. 提交补挂单：把 fillwatch 算出的买单经虚拟 `submit` 提交。
5. 执行器接单成交：`order_executor.py` 填单（模拟 fill）→ 入账 trade_log
（买入成交行带标记）→ quota A2 平衡（available = quota − deployed，
available=108780.74、quota=167708.27、deployed=58927.53）。
6. 闭环自洽：已入账的买入成交不再被当作新成交；未入账的卖出成交仍被检出
（compare 模式不入账，live 模式才会入账它）。

### 关键设计点（实测中发现并确认）

- **执行器填单即入账**：执行器在虚拟模式下填单时直接写 trade_log、更新 quota。
若先由执行器填单，fillwatch 再去看会判“已入账”而静默——这是**正确行为**
（与 test_fillwatch “已入账成交静默”一致），不是 bug。
- **因此闭环的“成交”一步必须用 virtual run 模拟**（只改 state、不写 trade_log），
与真实系统“成交在 cofool、入账由 fillwatch 做”的分工一致。
但 virtual run 实际也会写 trade_log，故测试中把它截回仅表头来模拟
“成交未入账”（与 test_fillwatch 场景 1 同一做法），fillwatch 才能检出新成交。
- **虚拟账本初始值不是 100 万整**：它镜像真实系统当前状态
（B=490341.72、A2=167708.27），故不以“四仓合计 100 万”断言；
平衡以每仓 `available = quota − deployed` 为准。
